Sieve under the profiler

Sieve injects 278 KB of JavaScript into the top frame of every page and 46 KB into every subframe, then runs up to thirteen independent whole-document MutationObservers on top of it. Most of that architecture is sound. Three things in it are not, and one of them — a single Array.prototype.shift() in a module that is on by default — burns half a second of pure CPU on a long page for work that costs 0.9 ms done correctly.

What implementing the audit proved wrong about it

Three of these recommendations did not survive being carried out. Each is corrected where it appears, and they are collected here because the pattern matters more than the individual errors: every one was a figure estimated rather than measured.

  • "Raise the ad-tracker poll to 5 minutes." Five minutes is the matched-rule retention window, so that cadence drops matches and under-reports silently. The code comment said so and the audit did not read it carefully enough. Shipped 2 minutes. (finding 8)
  • "Two one-minute alarms on a default install." Neither alarm exists by default — both belong to opt-in features. (section 01)
  • "Newline format for the tracker list, ~−1 MB." Measured at 191 KB on disk and 9 KB compressed. Withdrawn. (section 10, P3)
  • The byte counts on this page were ~2 KB light, and have been corrected. They were measured against a working tree, not a clean checkout. .gitattributes normalises line endings on checkout, so the CRLF files CI and every fresh clone build are slightly larger than the LF copies sitting in a tree that has been edited in place. Caught while setting the CI budget, by building two throwaway worktrees at the before and after commits and measuring both the same way. Every percentage on this page was unaffected — both endpoints moved together — and all of them survived re-measurement: −59.0%, −24.9%, −30.6%, −9.6%.

A fourth thing the audit got wrong in the other direction: it said the 284 KB of injected script cost only 3.5 ms to compile and was therefore a memory problem rather than a CPU one. That was right — but it undersold the fix, because the same work that halved the bytes also removed two per-page fetches, 68 KB of an opt-in feature, and three redundant executions of a 22 KB file.

One regression, introduced and then resolved. The P0–P2 work added ~11 KB of explanatory comments to the five scripts that run in every iframe, which briefly pushed the per-subframe payload above its starting point (48,700 → 58,782 B). P3's build-time strip took it to 36,557 B — below baseline. Worth recording because it is the failure mode of a comment-heavy house style meeting a byte budget, and the fix is a build step rather than writing less down.

01Performance audit summary

What the profiler actually says, as opposed to what the code comments promise. Every number below was measured, not estimated.

Sieve's newer modules are genuinely well engineered. content/facebook-ads-dom.js uses a leading-edge throttle with an armed flag, caps its pending roots, dedupes ancestors, filters disconnected nodes, and drains its own mutation records — that is the correct pattern, and it should be the template for everything else. content/anti-adblock-dom.js orders its predicates cheapest-first so innerText (a forced reflow) is only ever paid on candidates that already passed a free textContent check. The whole Ad & Trackers suite registers dynamically, so a user who never enables it pays literally nothing.

The problems are concentrated in three places: the always-on default modules (Bad Language, Dark Patterns), the older Popup-Hijack detectors, and the stats plumbing that every module writes through. In each case the pattern is the same — work that is correct on a 2,000-element demo page and superlinear on a real one.

16.7 ms — one frame at 60 Hz. Anything past this line is a dropped frame. A low-end device is 3–5× these figures.

The last bar is the useful control. Injecting a quarter-megabyte of source into every page — the thing that looks most alarming — costs 3.5 ms. The scans cost 20–140× that. Bundle size is a real problem here, but it is a memory and install-size problem, not a CPU one.

Idle behaviour

Not close to zero once features are enabled. A browser sitting untouched runs up to two independent one-minute chrome.alarms, each waking the service worker and re-evaluating the full 16-module import graph. An open YouTube tab additionally runs setInterval(skipAdIfPlaying, 250) in every frame, forever, with no document.hidden gate; an open Facebook tab runs a 5-second full-document sweep on the same terms.

Correction. An earlier draft of this section said "with defaults". That was wrong, and checking it while implementing the fix is what caught it: the usage-tracker heartbeat is only armed when Usage Insights is on (opt-in, off by default), and the ad-tracker stats poll only when an Ad & Trackers group is on (also opt-in). On a genuinely default install neither alarm exists. The finding stands for users who enable those features; the "every user pays this" framing did not.

Startup behaviour

Every page load pays: 3.5 ms of compile, five chrome.storage.local.get round-trips in the top frame plus three more per subframe, and — at document_idle — three separate full-document TreeWalker passes from three modules that never talk to each other.

02Top 10 performance problems

Ranked by measured impact, not by how wrong the code looks.

1. queue.shift() makes the text-node drain quadratic

P0Simple

content/bad-language.js:218  ·  content/profanity-filter.js:400

Cause. scheduleFlush() drains a queue of every text node on the page with scanQueue.shift(), 400 per idle slice. V8 has a fast path for shift() on small arrays, but past roughly 16k elements it degrades to a full memmove per call. The queue holds every text node in the document.

Why expensive. Each of the 400 shifts in a slice moves the entire remaining queue down one slot. At a queue depth of 128,000 that is 51 million element moves per slice, and there are 320 slices.

-   scanNode(scanQueue.shift());

An index cursor, plus a reset when the queue empties. Six lines, ~550× faster on a long page. Apply the identical change to profanity-filter.js.

2. Every recorded block rewrites the whole stats blob and broadcasts to every frame in every tab

P0Architectural

common/stats.js:65 recordBlock()  ·  senders in comment-collapse.js:148, overlay-detector.js:185, link-hijack-detector.js:129, dark-patterns.js:90

Cause. recordBlock() does a read–modify–write of the entire 30-day sieveStats object per event. Three callers send one message per item: comment-collapse fires once per collapsed comment, the two hijack detectors once per removed element.

Why expensive. One recorded block costs a service-worker wake, a storage.local.get, a storage.local.set (disk-backed LevelDB), and then a storage.onChanged broadcast that Chrome delivers to every listener with access — 17 in the service worker, 9 per top frame, 3 per subframe, in every open tab.

Two changes, both small. (a) In each content script, accumulate counts and flush once per second with a trailing timer, so a burst of 200 collapses becomes one message carrying count: 200 — the message shape already supports it. 3. Debounce starvation, unbounded queues, and layout thrash in the hijack detectors

P0Simple

content/overlay-detector.js:225–265  ·  content/link-hijack-detector.js:180–220  ·  content/dark-patterns.js:157–170

Cause. All three use a trailing debounce with no maximum wait:

clearTimeout(debounceTimer);
debounceTimer = setTimeout(flushMutations, 300);

On any page that mutates more often than every 300 ms — a feed, a carousel, a spinner toggling a class, a live ticker — the timer is cancelled before it can fire. Three consequences, all bad at once: the flush never runs (the feature silently does nothing), pending grows without bound (there is no cap on the push, only on the collection), and it holds strong references to detached DOM nodes.

The flush itself is the other half. isHijackOverlay() calls getBoundingClientRect() then getComputedStyle() per candidate, up to MAX_CANDIDATES = 3000. Interleaving reads that way forces a style-and-layout recalculation per element.

Copy the pattern already used correctly in anti-adblock-dom.js:495: a leading throttle guarded by a scheduled flag, so the first burst flushes at 150 ms and subsequent ones coalesce. Almost no element covers 80% of the viewport, so the second pass will normally be empty.

6. Shortener resolution rebuilds a dozen 200k-entry Sets per click, inside a 3-second deadline

P1Architectural

background/url-shortener-checker.js:163 checkResolvedUrl()

Cause. For every click on a shortener link, the checker walks 13 categories. Each builds a fresh Set from a fresh fetch and parse. getGamblingDomains() additionally calls chrome.declarativeNetRequest.getDynamicRules(), which marshals the full gambling ruleset — up to 400,000 domain strings packed 10,000 to a rule — across the IPC boundary. Nothing is memoised.

Why it matters more than the raw cost. The content script gives this a hard RESOLVE_TIMEOUT_MS = 3000 and fails open. On a slow machine the check loses that race, so the user's click is delayed by three seconds and the protection silently does not apply.

Fix

Replace the whole hand-rolled matcher with chrome.declarativeNetRequest.testMatchOutcome(), which asks the engine that already holds these rules whether a URL would be blocked, natively, with no Sets and no marshalling. The declarativeNetRequestFeedback permission is already in the manifest. Keep the manual path as the Firefox fallback, but memoise each category's Set at module scope and invalidate on storage.onChanged.

7. The offscreen toxicity document is never closed

P1Simple

background/service-worker.js:633 ensureOffscreenDoc(), :672 the only closeDocument()

Cause. The document is created on the first classify request and closed only when toxicModelEnabled flips to false. Close every YouTube and Reddit tab and it stays resident, holding the TensorFlow.js runtime and a ~55 MB model, for the rest of the browser session.

Fix

An idle timer. Record lastClassifyTs on each relay; on a 5-minute alarm, if nothing has been classified for 10 minutes, call chrome.offscreen.closeDocument(). ensureOffscreenDoc() already handles recreation, so the next classify just pays one reload.

8. Two independent one-minute alarms keep the service worker awake forever

P1Simple

background/ad-tracker-stats.js:73 POLL_MINUTES = 1  ·  background/usage-tracker.js:48 HEARTBEAT_MINUTES = 1  ·  usage-tracker.js:356 top-level start()

Cause. Two alarms on independent one-minute periods mean up to two service-worker wakes per minute, each re-evaluating the full import graph of 16 background modules plus keyword-pattern.js. Worse, usage-tracker.js calls start() at module top level — so every wake, from any cause, runs a storage read, an alarms.create, and (when enabled) a resync() that queries the focused window, the active tab and the idle state, then writes the open segment back to storage.

Fix

(a) Raise the ad-tracker stats poll from 1 minute to 2. (b) Guard the top-level start() so a wake with tracking disabled does nothing but return — it currently calls schedulePrune() and clearOpenSegment() (a storage write) on every wake, for a feature that is off.

Corrected from an earlier draft, which said to raise the poll to 5 minutes and to merge the two alarms. Both were wrong. The comment above POLL_MINUTES spells out why: matched rules not tied to an open document are dropped after five minutes, so polling at five would miss any match made just after the previous poll and under-report silently. Two minutes is a quarter of the API quota with 2.5× headroom against retention. And the usage-tracker heartbeat cannot simply be merged or slowed: LIVENESS_GRACE_MS is derived from it (2 × HEARTBEAT_MS), so lengthening it widens the window in which a suspended machine can bank time it did not spend — degrading the accuracy that is the whole point of that feature. It stays at one minute, and it only runs when the user has opted in.

9. A 250 ms polling timer on YouTube, in every frame, that never stops

P1Simple

content/youtube-ads.js:729  ·  registered with allFrames: true (background/youtube-ads.js:49)

Four times a second, in every frame of every YouTube tab, forever: document.querySelector("video"), an adOnScreen() check, and sometimes a second three-selector query. Frames that contain no video pay it too. There is no document.hidden gate, so a backgrounded or pinned tab keeps the timer alive and blocks the renderer from entering deep idle.

Fix

Cache the <video> element (refresh it from the existing observer rather than re-querying), return immediately when document.hidden, and start the interval lazily — only once a video element has actually been seen in this frame. The polling rationale in the comment is sound; the cost is in re-querying and in running where there is nothing to find.

10. Every subframe independently reads storage at document_start

P1Simple

content/popup-hijack-bridge.js:104  ·  content/overlay-detector.js:48  ·  content/link-hijack-detector.js:49

Three all_frames scripts each issue their own chrome.storage.local.get. They all want the same key. On a page with 40 iframes that is 123 IPC round-trips to the browser process at document_start — the most latency-sensitive moment in the page's life — and 123 storage.onChanged listeners left registered afterwards.

Fix

They are already loaded as one manifest entry and share an isolated world. Have the bridge do the single read and hand the result to the other two through a shared window.__sieveHijackConfig promise. Three reads become one. Register one storage.onChanged listener that fans out in-process.

03CPU optimization opportunities

Beyond the top ten — what else burns cycles, and what turns out not to.

11. Eight case-insensitive substring attribute selectors, per sweep

P2Simple

content/anti-adblock-dom.js:349 WALL_SELECTOR

[class*='adblock' i] and its seven siblings are the slowest selector shape in Blink: no fast path, so the engine walks every element doing a case-folding substring search. Measured at 13.5 ms per call over 20,000 elements, and candidates() calls it on every sweep — six timed sweeps plus one per mutation burst.

Fix

Run the full WALL_SELECTOR query only on the six timed sweeps. Mutation-driven sweeps already have their candidates in pending and do not need to re-scan the document. Alternatively, drop i from the class selectors and pair each with its lowercase form — class names are effectively case-sensitive in practice, and the pair is far cheaper than the flag.

12. Prototype patches installed even when the module is off

P2Simple

content/popup-hijack-blocker.js:297, :306, :337, :360

window.open, HTMLAnchorElement.prototype.click, HTMLFormElement.prototype.submit and EventTarget.prototype.dispatchEvent are all replaced unconditionally at document_start, in the MAIN world, in every frame. The enabled flag is checked inside the replacement. Popup Hijack is off by default, so every user pays this for a feature they have not turned on.

dispatchEvent is the one that matters — it is on the hot path of every React app and every custom event bus, and the wrapper's nativeDispatch.apply(this, arguments) forces an arguments-object materialisation per call.

13. collectBlocks() is O(n²) in contains(); pathMatches() compiles a RegExp per test

P2Simple

content/search-filter.js:353–392  ·  common/search-filter.js:66 pathMatches()

Each candidate is tested against every other candidate with contains(), then against everything already found. Measured at 0.2 ms for 50 candidates, 1.4 ms for 200, 12.5 ms for 600 — the quadratic curve is plainly visible. A Google SERP with continuous scroll reaches the high hundreds.

Separately, pathMatches() calls new RegExp(...) on every invocation. It early-returns for bare-domain rules (the common case), but a user with path-scoped rules pays a fresh compile per rule per result.

Fix

Replace the double some() with a single downward pass: sort candidates by DOM order (they already are, from querySelectorAll), keep a reference to the last accepted block, and skip any candidate it contains. That is O(n). For pathMatches, compile the path regex once in compile() and store it on the rule beside host and path.

14. Every list entry is validated twice, with ReDoS probes both times

P2Simple

common/keyword-pattern.js:381 compileList()

compileList() calls parseListEntry(), then validateListEntry() (which parses again and runs the timing probes), then compileEntry() (which validates and probes a third time). Instrumenting RegExp.prototype.test shows 32 calls to compile a single /regex/ entry.

The absolute cost is modest — 7.4 ms for a 2,000-entry list with 100 regexes — but it is paid on every page load, in every tab, by custom-block.js, and again by search-filter.js on every SERP.

Fix

Have compileList() parse once and pass the parsed entry down, and give compileEntry() an internal variant that skips re-validation when the caller has already validated. Cuts the probe work in half with no change to the safety guarantee.

15. chooseTarget() reads textContent at every ancestor level

P3Simple

content/patterns/timers.js:109–124

Walking from a timer element up to document.body, reading node.textContent (an O(subtree) serialisation) and getComputedStyle at each level, is O(depth × subtree). It only runs on confirmed decreasing timers, so it is rare — but it is unbounded on a deep DOM.

Fix

Stop climbing once textContent.length exceeds the 80-character ceiling; length only grows going up, so every further level is guaranteed to fail the test.

Measured and found not to be a problem

Two things that look expensive and are not, so they should be left alone:

  • The 942-term profanity alternation regex. Applied to three text variants per comment, it costs 24 µs per comment — V8 handles a flat alternation well. 5,000 comments cost 118 ms of regex, spread across idle slices. Not worth restructuring into a trie.
  • extractText()'s per-comment TreeWalker. 2.4 ms for 2,000 comments. Fine.

The cookie engine is the biggest avoidable retention

When Auto-reject is on, every page load constructs new CMP(key, config[key]) for all 204 CMPs in data/cookie-rules.json — each building its Detectors, Matchers, Actions and Consents recursively. Five seconds later the engine gives up and calls stopObserver(), but ConsentEngine.singleton still points at the whole graph, and rulesCache still holds the parsed JSON. Nothing is collectable until the tab closes.

Fix

In the handled: false branch of onHandled(), null out ConsentEngine.singleton and rulesCache. Better still, filter the rule set before constructing: most CMPs can be excluded by a cheap pre-check on their detector's root selector, so a typical page constructs a handful of CMPs rather than 204.

Long-session behaviour

The two unbounded pending arrays are the only true unbounded growth. Everything else is bounded per tab and released on navigation. WeakSet is used correctly for seen in anti-adblock-dom.js and queued in profanity-filter.js; explanations in search-filter.js is a WeakMap. Those are right.

05DOM & content-script optimization

What runs where, how often, and how much of it is unnecessary.

Thirteen whole-document observers

With everything enabled, a single page carries up to thirteen independent MutationObservers, most rooted at document.documentElement with subtree: true, and four of them also watching attributes. Chrome delivers a separate copy of the record set to each: an instrumented test appending 300 cards produced 300 MutationRecords with one observer and 3,900 with thirteen. The cost is allocation pressure and GC, not dispatch.

Fix — architectural

Introduce common/dom-watch.js: one MutationObserver on documentElement with the union of the options, which coalesces records and dispatches to registered subscribers with a leading throttle. Scripts that run where they are not needed

  • cookie-engine.bundle.js (58 KB) is injected into every page whether or not Auto-reject is on. It is opt-in and off by default, so the overwhelming majority of users parse 58 KB on every page load for a feature they never enabled. Move both cookie scripts to chrome.scripting.registerContentScripts, exactly as the Ad & Trackers suite already does.
  • url-shortener-intercept.js fetches its list before checking its toggle (line 31 vs line 131), in every frame. Read the setting first; fetch the list lazily on the first click of a link whose hostname might match. Also cache the toggle instead of re-reading storage inside the click handler.
  • The overlay and link-hijack detectors run in every subframe for a feature that is off by default. An invisible full-viewport click-catcher inside a 300×250 ad iframe is not a threat worth a per-frame observer; consider allFrames: false, or register them dynamically.
  • keyword-pattern.js is listed in three separate <all_urls> manifest entries and has no idempotence guard, so it is parsed and fully executed three times per top frame (four on comment sites) — 66 KB where 22 KB would do.

06Background / service-worker optimization

MV3 charges by the wake. Sieve wakes a lot.

Wake sources

The worker imports 16 modules at top level and registers 17 storage.onChanged listeners, 6 runtime.onMessage listeners, 4 alarm handlers and 2 webNavigation listeners. Every one of those is a wake source, and a wake re-runs the whole import graph.

16. webNavigation.onBeforeNavigate has no filter

P2Simple

background/service-worker.js:703

The listener fires for every frame of every navigation in every tab — including iframes, prerenders, about:blank and the extension's own pages — and only then does if (d.frameId !== 0) return;. The filtering happens after the wake. On a page with 40 iframes that is 40 dispatches for one useful event.

Fix 
chrome.webNavigation.onBeforeNavigate.addListener(
  handler,
  { url: [{ schemes: ["http", "https"] }] }   // filtered in the browser process
);

The filter is applied before the event crosses to the worker, so non-http navigations stop waking it at all.

17. Editing the blocked-sites list marshals the entire gambling ruleset, twice

P2Simple

background/service-worker.js:288 applyCustomBlocks(), :323 applyAllowlist()

Both call chrome.declarativeNetRequest.getDynamicRules() with no filter, purely to compute a removeRuleIds list from a known ID band. That call returns every dynamic rule, including the gambling big list packed 10,000 domains to a rule — several megabytes of strings across the IPC boundary. Then it happens again for the allowlist. getDynamicRules() appears at seven more call sites on the same pattern.

Fix

Keep the installed ID list for each band in chrome.storage.session when the rules are written, and read that instead. Where a read is unavoidable, pass the { ruleIds } filter. At minimum, share one getDynamicRules() result between applyCustomBlocks() and applyAllowlist() — they already run on the same write chain.

Listener hygiene

Seventeen storage.onChanged listeners each run their own key check on every write. Individually cheap; collectively it means the frequent sieveStats write (finding 2) runs 17 handlers for a key none of them care about. A single dispatcher keyed by storage key — onKeyChange("gamblingEnabled", fn) — would make the fan-out proportional to what actually changed. Worth doing after finding 2 lands, when the write rate is already down.

07Network & storage optimization

Network

Sieve makes almost no runtime network requests, and the ones it makes are correct: the gambling list is fetched on a weekly alarm, the safety lists on their own schedules, and the toxicity model is downloaded once into the Cache API with resumable per-file progress and a decompressed-size integrity check. Nothing is fetched per page or per request. This area is in good shape.

The exception is fetch(chrome.runtime.getURL(...)) for bundled data, which happens per page and per frame:

Fix

The two word lists total 865 bytes across 50 entries. Inline them as a JS constant and delete both fetches, the loadJson helper and the async wait before the first scan — that also removes a round-trip from the critical path. Move the shortener list behind the toggle check. For cookie-rules.json, parse once in the service worker and hand tabs the subset they need, rather than parsing 456 KB per tab.

Storage

The storage.local hot path is already well managed: the big fetched blocklists live in IndexedDB (background/list-store.js), and the options page does one batched read. Two problems remain.

  • Write frequency. recordBlock() (finding 2) and doomscroll.js's 5-second flushStats() both do read–modify–write of a whole object. The doomscroll one is bounded and fine; the stats one is not.
  • Read duplication at document_start. Five separate storage.local.get calls in the top frame, three more per subframe (finding 10). These are the page's first milliseconds; each is an IPC round-trip.
Fix

Add common/settings-cache.js: one storage.local.get per frame for the union of keys every content script needs, exposed as a promise on the isolated world, with one storage.onChanged listener fanning out in-process. Eight reads and twelve listeners become one and one.

09Architecture improvements

Four shared primitives that would fix whole classes of problem rather than instances of them.

A. One mutation dispatcher

common/dom-watch.js — a single observer, one throttled dispatch, subscribers declaring their interests. Collapses thirteen record sets into one, and makes the correct throttle (leading edge, bounded queue, takeRecords() after self-writes) the default rather than something each module reimplements. Three modules currently get it wrong. Fixes findings 3, and prevents the next one.

B. One text walk

common/text-scan.js — one TreeWalker over the document, offering each non-blank text node to registered visitors, in idle slices with an index cursor. Bad Language, Timers and Scarcity register instead of walking. Fixes findings 1 and 4 together, and gives the blank-node skip to all three at once.

C. One settings read per frame

common/settings-cache.js — one storage.local.get, one onChanged listener, a synchronous accessor afterwards. Eight reads and twelve listeners per frame become one and one. Fixes findings 10 and the read half of 7.

D. Buffered stats

Increments accumulate in memory in the content script and in the worker; both flush on a timer. Fixes finding 2, and removes the single largest source of unnecessary service-worker wakes and storage writes.

All four are additive modules that existing code opts into one at a time. None requires a rewrite, and each can land and be measured independently.

A note on the default-on set

Bad Language, Dark Patterns and the Toxic Comment Hider are all on by default, and between them account for most of the per-page cost measured here. That is a product decision, not a performance bug — but it does mean these three modules deserve a stricter performance standard than the opt-in ones, and today they have the weakest implementations in the codebase. The opt-in Ad & Trackers suite, which the user has to deliberately enable, is the best-written. That is backwards.

4. Memory over a long session

DevTools Memory panel, heap snapshot after opening 20 tabs across a session and closing them again. Compare snapshots an hour apart on a page that mutates continuously (a live sports scoreboard is a good adversary for the debounce-starvation case).

  • Regression test for the leak: assert that pending.length in overlay-detector never exceeds its cap after 60 seconds on a page mutating every 100 ms. Today it grows without bound; that is a testable invariant.
  • Offscreen document: confirm it disappears from chrome://inspect/#other ten minutes after the last comment page is closed.
  • Cookie engine: take a heap snapshot after the 5-second give-up and assert the 204 CMP objects are collectable.

5. Storage write rate

The cheapest continuous signal, and the one that will regress first. Wrap chrome.storage.local.set in the service worker with a counter during development:

// dev only
let writes = 0;
const _set = chrome.storage.local.set.bind(chrome.storage.local);
chrome.storage.local.set = (...a) => { writes++; return _set(...a); };
setInterval(() => console.log("[perf] storage.set/min:", writes, (writes = 0)), 60000);

Baseline on a Reddit thread with 200 collapsed comments: 200+ writes in a few seconds. Target: fewer than 5 per minute at steady state.

6. Injected bytes and package size

Both are exactly computable in CI, so both should be asserted rather than measured. Add a check to the build that fails if the <all_urls> top-frame total exceeds a budget (start at 220 KB, down from 284 KB) or the package exceeds 2.5 MB. A budget that fails the build is the only kind that holds.

7. Reproducing this audit's numbers

Every figure here came from synthetic pages driven through headless Chrome, which avoids the Browser-pane compositing problem noted in this project's own notes. The shape is:

chrome --headless=new --disable-gpu --no-sandbox --dump-dom bench.html

One caveat worth recording: do not pass --virtual-time-budget when timing anything. It freezes performance.now(), and every measurement after the first comes back as 0.0 ms. Use Date.now() over a loop of N iterations instead.

—Already optimized — leave alone

Things that look like they need attention and do not. Changing these would be churn.

  • Dynamic content-script registration for the whole Ad & Trackers suite. ad-slot-collapse, anti-adblock, float-video, youtube-ads and facebook-ads all register through chrome.scripting.registerContentScripts and unregister when off. A user who never enables them pays exactly nothing. This is the correct pattern and the manifest-declared scripts should move toward it, not away.
  • facebook-ads-dom.js's scheduling. Leading-edge throttle behind an armed flag, MAX_PENDING_ROOTS cap, ancestor deduplication, isConnected filtering of stale roots, deliberate refusal to observe attributes, and a visibilitychange re-arm. It is the reference implementation in this codebase.
  • anti-adblock-dom.js's predicate ordering. Raw length → textContent regex → innerText (the reflow) → geometry. The comment explaining why innerText comes third is exactly right, and the observer.takeRecords() after self-writes is the correct cure for a self-feeding observer.
  • The 942-term profanity regex. 24 µs per comment, measured. Do not restructure it into a trie.
  • Big lists in IndexedDB. background/list-store.js keeps the multi-megabyte fetched blocklists off the storage.local hot path, which is what makes settings reads instant. The reasoning in that file's header is correct.
  • The options page's batched read. One storage.local.get(optionsDefaults()) plus a loading veil, instead of per-control reads.
  • tracker-domains.json parsing. Only on rule (re)build — install, startup, a toggle flip, an allowlist edit. Never on a request path. The file is too big, but when it is read is right.
  • doomscroll.js's scroll handler. Passive listeners doing two Date.now() calls and some arithmetic. Correct.
  • float-video.js's scoping. Ancestor walks with getComputedStyle happen only for real <video> and known player iframes, never for arbitrary elements. The comment explaining why it does not observe attributes shows the trap was seen and avoided.
  • Early exits in search-filter.js and custom-block.js. A hostname test and an empty-list test respectively, both before any work. Both are why these files cost nothing on the pages where they have nothing to do.
  • Model download and caching. Resumable, per-file, integrity-checked against decompressed sizes, mirrored. Nothing to improve except when the loaded model is released.
